# SV32 core

SV32 is a single-cycle [RISC-V](https://riscv.org/) RV32I core written in
DSLX. The design demonstrates the full XLS flow used by this project:
type-checked DSLX, optimized IR, an entirely XLS-generated clocked Verilog core,
and RTL simulation checked against an independent Python model.

## Modeling approach

The complete core is described in DSLX:

- `src/sv32/sv32_execute.x` contains the pure instruction function
  `step(state, imem_rdata, dmem_rdata) -> (state', dmem_req, halt)`.
- `src/sv32/sv32_core.x` contains the stateful `sv32_core` proc. Its `init`
  zeros the PC and register file; its `next` invokes `step`, emits memory and
  debug outputs, and preserves architectural state on halt.
- `scripts/build-sv32.py` converts the proc to IR and invokes XLS codegen.
  The complete `sv32_core.v`, including state registers and asynchronous reset,
  is the unmodified output of XLS. There is no hand-written core RTL template.
- `sv32_top.sv` is a wiring-only compatibility alias, outside the core.
  ROM, RAM, LED MMIO, and board integration remain in Verilog.

### Channels and scheduling

The pinned DSLX frontend emits streaming channels. The build adapts only the
proc's channel metadata to XLS `single_value` channels and removes the frontend's
leading underscore from port identifiers before optimization. This creates plain
wires without ready/valid signals. The adapter checks the expected channel names,
directions, and attributes and rejects unexpected frontend output. It does not
modify state, initialization, next-state expressions, or generated Verilog.
The frontend behavior is in the pinned XLS
[channel conversion source](https://github.com/google/xls/blob/6e55d7763/xls/dslx/ir_convert/channel_scope.cc).

The build uses `--generator=pipeline --pipeline_stages=1`, with input/output
flopping disabled. Each activation executes one instruction per clock, with no
extra startup cycle. The `unit` delay model is only for scheduling; physical timing
must be checked separately in Quartus. Increasing the stage count requires a
memory protocol/controller redesign; it is not a drop-in frequency adjustment.
The generated signature is checked for zero I/O latency and an initiation
interval of one. See the upstream [codegen options](https://google.github.io/xls/codegen_options/)
for reset and I/O flopping controls.

Instruction memory reads from the current PC combinationally. The data-memory
address depends on the current state and instruction, and returned load data
feeds the next state. There is no combinational feedback through the load address.

### State and reset

```text
State    { regs: u32[32], pc: u32 }     // x0 remains zero
DMemReq  { addr: u32, wdata: u32, wstrb: u4 }
```

XLS implements proc state as registers and may optimize unused state bits.
There is no public packed state input/output. `debug_regs[32*i +: 32]` observes
register `xi`; `debug_pc` observes the current PC.

Codegen supplies asynchronous active-low `rst_n` for state storage. DSLX cannot
read that implicit codegen reset, so a single-value input `reset_n` suppresses
store strobes in the proc. **Connect `reset_n` and `rst_n` to the same signal.**
The Verilog SoC and compatibility alias already do this. The alias keeps the
original public interface for existing callers. A direct core instance uses:

```verilog
sv32_core cpu (
    .clk(clk), .rst_n(rst_n), .reset_n(rst_n),
    // ... memory and debug ports ...
);
```

### Public ports

| Port | Direction | Width | Description |
| --- | --- | --- | --- |
| `clk`, `rst_n` | in | 1 | Clock and asynchronous active-low reset |
| `reset_n` | in | 1 | Core only: connect to `rst_n`; `sv32_top` ties it internally |
| `imem_addr` | out | 32 | Instruction fetch byte address (`pc`) |
| `imem_rdata` | in | 32 | Instruction word at `imem_addr` |
| `dmem_addr` | out | 32 | Data address (word-aligned) |
| `dmem_wdata` | out | 32 | Store data, shifted into the addressed byte lanes |
| `dmem_wstrb` | out | 4 | Byte write strobes; zero during reset |
| `dmem_rdata` | in | 32 | Data word at `dmem_addr` |
| `halted` | out | 1 | High after ECALL/EBREAK or an illegal instruction |
| `debug_pc` | out | 32 | Current PC (simulation/debug) |
| `debug_regs` | out | 1024 | Optional observation: `xi` at `[32*i +: 32]` |

Instantiate `sv32_core` directly and compile `sv32_core.v`. The debug outputs
may be left unconnected. `--module-name review_core` renames the generated core
to `review_core`, while the compatibility alias remains `sv32_top`.

Memories are Harvard-style and byte-addressed, with 32-bit word lines and
little-endian byte lanes. Instruction memory is read-only. Reads must be
combinational and stores are accepted on rising clock edges; there is no
ready/valid or wait-state interface. Reset clears the PC and register file
and suppresses stores. The core freezes its state while `halted` is asserted.
Unsupported opcode/`funct3`/`funct7` combinations halt with the current PC
and registers preserved and no memory request. ECALL/EBREAK also preserve
the current state. This is the project's halt policy; architectural traps
are not implemented. CSR encodings remain NOPs. Reserved FENCE operand and
mode fields are ignored, as required by the
[RV32I specification](https://docs.riscv.org/reference/isa/v20260120/unpriv/rv32.html).

## Instruction support

| Class | Instructions | Notes |
| --- | --- | --- |
| Upper immediate | `LUI`, `AUIPC` | Complete |
| Jumps | `JAL`, `JALR` | Link writes `pc + 4`; `JALR` clears bit 0 |
| Branches | `BEQ`, `BNE`, `BLT`, `BGE`, `BLTU`, `BGEU` | Signed and unsigned |
| Loads | `LB`, `LH`, `LW`, `LBU`, `LHU` | Sign/zero extension; little-endian |
| Stores | `SB`, `SH`, `SW` | Byte strobes; 16/32-bit writes |
| Integer | `ADDI`, `SLTI`, `SLTIU`, `XORI`, `ORI`, `ANDI`, `SLLI`, `SRLI`, `SRAI` | Immediate arithmetic and shifts |
| Register | `ADD`, `SUB`, `SLL`, `SLT`, `SLTU`, `XOR`, `SRL`, `SRA`, `OR`, `AND` | Complete base `OP` set |
| System | `ECALL`, `EBREAK` | Halt the simulation |
| Memory ordering | `FENCE` | No-op for this in-order core |

Not implemented: CSR instructions (treated as NOPs), `MRET`/`WFI`, the `M`,
`A`, `C`, `F`, and `D` extensions, misaligned accesses, and traps. See the
header of `sv32_execute.x` for the authoritative list.

## Generate and test

```bash
python3 scripts/build-sv32.py     # DSLX -> IR -> clocked core + wrapper
python3 scripts/test-sv32.py      # DSLX tests, RTL build, and simulation
```

`test-sv32.py` runs the DSLX unit tests with the LLVM JIT, builds the RTL,
then simulates a demo program with Icarus Verilog and compares every register
and every data-memory word against `tests/sv32/sv32_ref.py`, followed by the
directed regression programs. To simulate a previous build directory without
rerunning the DSLX checks:

```bash
python3 scripts/test-sv32.py --simulate-only build/sv32
```

The default target is the clocked core named in `config.json`. To exercise
the compatibility wrapper explicitly:

```bash
python3 scripts/test-sv32.py --simulate-only build/sv32 --top-module sv32_top
```

A faster toolchain smoke test (DSLX tests plus Verilog generation, no
simulation) is available through `./bin/run-smoke-test.sh`.

## Verification

- `tests/sv32/sv32_test.x` exercises each instruction class by
  calling `step` directly: 23 unit tests cover ALU results, sign extension,
  branches, jumps and links, loads and stores, `x0`, `ECALL`/`EBREAK`, and
  `FENCE`, plus shift-count masking, both halfword lanes, unsupported
  encodings, and preserved state on halt.
- `tests/sv32/sv32_ref.py` is an independent interpreter written in
  Python. It includes an assembler and a demo program that loops, stores,
  reloads, performs byte accesses, and calls a subroutine.
- `tests/sv32/sv32_cases.py` supplies 35 programs, including independently
  specified register, memory, and halt-PC expectations for the directed cases.
- `scripts/test-sv32.py` checks the generated hardware against that model
  over all 32 registers and 256 data words, including halt PCs and cycle
  counts. The testbench verifies that reset suppresses store strobes and
  preserves memory even with a store at the reset vector. Simulation logs
  and inputs for directed programs live in `build/sv32/cases/<name>/`.
- `tests/sv32/test_build_sv32.py` builds default and custom core module names,
  checks standalone Verilog-2005 elaboration, and runs all 35 programs through
  both public cores and their compatibility wrappers. It also runs
  `reset_halt_tb.sv` for all four combinations: asynchronous reset with a stopped
  clock, store suppression during reset, consecutive dependent instructions,
  halt hold, and restart after mid-program or halted-state reset. Run it with:

  ```bash
  python3 -m unittest discover -s tests/sv32 -p 'test_*.py' -v
  ```

## Build artifacts

Generated files live under `build/sv32/` and are ignored by Git:

- `sv32.dslx.ir` — original proc IR from the DSLX frontend
- `sv32.ir`, `sv32.opt.ir` — single-value-channel proc IR before/after optimization
- `sv32.schedule.textproto` — one-stage proc schedule
- `sv32_core.v` — complete clocked core emitted directly by XLS
- `sv32_core.sig.textproto` — public core interface
- `sv32_top.sv` — compatibility wrapper around the public core
- `imem.hex`, `dmem.hex`, `tb.sv`, `sim.vvp` — simulation inputs and binary
- `config.json` — core name, DSLX top, channel kind, schedule, and reset data port
- `smoke-test.log` — output from the latest smoke test
